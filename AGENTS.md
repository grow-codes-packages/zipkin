# AGENTS.md — Grow Codes SDK for Zipkin (`zipkin`)

Instructions for AI coding agents and humans working in this repository. `CLAUDE.md` is a symlink to
this file. Service-specific notes (vendor quirks, API coverage, emulator limits) live in
`docs/compatibility.md`, the README "Function overview" and `skills/zipkin-sdk/SKILL.md`.

## What this repository is

One API for Zipkin in five languages, generated from
[sdk-kit](https://github.com/grow-codes-packages/sdk-kit) (version in `.sdk-kit.json`) and
completed with service code. Categories: **tracing**. The contract for every package is the
sdk-kit specification (`SPEC.md` in sdk-kit): names, defaults, error codes, environment variables,
category interfaces and the Docker contract.

Generated folders inside each package: `core`, `secrets`, `logging`, `tracing` and `testing`
(Go: files prefixed `core_`, `secrets_`, `logging_`, `tracing_`, plus `testkit/`; Python: `_core/`,
`_secrets/`, `_logging/`, `_tracing/`, `testing/`). Everything else — the client, the config and the
service modules — is service code.

## Generated files rule

- A file whose first lines contain `Generated by sdk-kit <version> — do not edit` belongs to sdk-kit.
  **Do not edit it here.** Change sdk-kit (template), release it, then run `sdk-kit sync` in this
  repository. A local edit is detected (`.sdk-kit.json` keeps a SHA-256 per file) and blocks the
  next sync until it is reverted or forced.
- To take over a generated file for good, delete its header line; sync then leaves it alone.
- Never edit `conformance/` or `.sdk-kit.json` by hand.
- `sdk-kit check` (run in CI) verifies that the required files, badges and workflows are present.

## API parity rule

The five packages expose the **same** functions, options, defaults, error codes and behaviour. Any
change to the public API lands in all five languages in the same pull request, with unit tests in
each and an integration call in the Docker suite. Names follow each language's convention:

| | TypeScript | Rust | Go | Python | Java |
| - | - | - | - | - | - |
| Methods | `camelCase` | `snake_case` | `PascalCase`, `ctx` first | `snake_case` | `camelCase` |
| Errors | `ZipkinError` + subclasses | `Error` enum, `code()` | `*Error`, `errors.Is(err, zipkin.ErrNotFound)` | `ZipkinError` + subclasses | `ZipkinException` + subclasses |
| Durations | `…Ms` numbers | `Duration` | `time.Duration` | seconds (`…_s`) / `timedelta` | `Duration` |
| Async | `Promise` + `AbortSignal` | `async` + `blocking` feature | sync with `ctx` | sync + `AsyncZipkinClient` | sync + `…Async` |

If one language truly cannot support something, document it in `docs/compatibility.md`.

## Tests and coverage

- Unit tests run against local mock HTTP servers; they never need network access or Docker.
- **Coverage gates** (CI-enforced, first-party code only): TypeScript, Python and Java ≥ 90 % lines
  **and** ≥ 90 % branches; Rust ≥ 90 % lines and ≥ 90 % regions; Go ≥ 90 % statements.
- Unit conformance tests are named after the ids in `conformance/core-unit.md`.
- Test fakes for users of the package ship in the testing module (TypeScript
  `@grow-codes/zipkin/testing`, Rust feature `testing`, Go `testkit`, Python
  `grow_zipkin.testing`, Java `codes.grow.packages.zipkin.testing`).

## Docker integration rules

- `docker/compose.yml` runs `openzipkin/zipkin:3.6.1` plus a one-shot `bootstrap` service that writes credentials
  to `/bootstrap/env`. Tests read that file and `GROW_ZIPKIN_URL`.
- Each language has a `test-<lang>` service (profile `<lang>`). Its Dockerfile packs the package and
  installs it into the consumer project in `<lang>/integration/`, which runs the integration tests
  and the conformance runner.
- Always run through `make test-docker`: it uses a unique Compose project per run, publishes no host
  ports and always runs `docker compose down -v`, even on failure or Ctrl-C.
- Every public function is called at least once against the real service with a round-trip
  assertion. Functions the service cannot serve are listed in `docs/compatibility.md` and covered by
  unit tests.

## Release rules

- Releases are made by [release-please](https://github.com/googleapis/release-please) from
  Conventional Commits on `main` (`feat:`, `fix:`, `feat!:`). Never bump versions or edit
  `CHANGELOG.md` by hand. Use the language as the scope when a change touches one package.
- One release pull request covers all five packages. Tags: `typescript-vX.Y.Z`, `rust-vX.Y.Z`,
  `go/vX.Y.Z` (the Go module lives in `go/`, so its tag must be `go/v…` for `go get` to work),
  `python-vX.Y.Z`, `java-vX.Y.Z`.
- The release workflow publishes to npm, crates.io, PyPI and Maven Central; Go is published by its
  tag. Publishing credentials live only in the release environment of the GitHub repository.

## Zipkin specifics

- **Service modules** (service code in every language): config + client, `reporter`
  (`ZipkinReporter`, v2 JSON ingest), `query` (`ZipkinQueryClient` = native v2 query API +
  `TraceQueryClient`), `model` (`ZipkinSpan`/`Endpoint`/`Annotation`/`ZipkinDependencyLink`,
  normalization, span ↔ SPEC mapping), `exporter` (`ZipkinSpanExporter` on the official SDK
  `SpanExporter`) and `setup` (`initTracing`, env resolution, propagator order). File map:
  TypeScript `src/{client,config,reporter,query,model,exporter,setup}.ts`; Rust
  `src/{client,config,reporter,query,model,exporter,setup,blocking}.rs`; Go
  `{client,client_extra,config,reporter,query,model,exporter,tracing}.go`; Python
  `src/grow_zipkin/{client,config,_http,reporter,query,model,exporter,setup}.py`; Java
  `codes.grow.packages.zipkin.{ZipkinClient,ZipkinConfig,ZipkinReporter,ZipkinQueryClient,ZipkinSpan,
  ZipkinSpanExporter,ZipkinTracing,…}`.
- **Binding decisions** (keep all five languages on them):
  - Our own `ZipkinSpanExporter` in every language (no OpenTelemetry Zipkin exporter dependency);
    the span mapping table in `docs/functions/tracing-setup.md` is the contract (remote endpoint =
    service name only, resource attributes other than `service.name` not copied, event
    attributes keep their JSON type, `unknown_service` fallback, no `debug`/`shared`).
  - Propagators default `tracecontext, baggage, b3` (B3 single), composed B3 first so W3C wins.
  - `protocol` default `native`; `grpc`/`http/protobuf` only to an OpenTelemetry Collector (an
    OTLP endpoint ending in `/api/v2/spans` is `CONFIG`).
  - Env: `GROW_ZIPKIN_URL` > `ZIPKIN_URL` > base of `OTEL_EXPORTER_ZIPKIN_ENDPOINT`; span
    endpoint `GROW_ZIPKIN_ENDPOINT` > `OTEL_EXPORTER_ZIPKIN_ENDPOINT` > `<url>/api/v2/spans`;
    tracing also `GROW_ZIPKIN_PROTOCOL`, `GROW_ZIPKIN_COMPRESSION`, `OTEL_EXPORTER_ZIPKIN_TIMEOUT`.
    No token: gateway credentials go in `headers`.
  - `getTraceSpans` = raw spans or null; `getTrace` = normalized `Trace` or null (404 → null).
  - `getTraceMany`: `[]` without a request for no ids, dedupe (16 = padded 32), request order,
    chunks of 100 (Zipkin answers 414 above ~4 KB of URL).
  - `searchTraces` without `start` = the last hour, limit 20; `getTraces` keeps server defaults.
  - Tag terms containing ` and ` (or `=` in a key) are matched client-side; `buildAnnotationQuery`
    rejects them.
  - `ZipkinDependencyLink.errorCount` defaults to 0 (the SPEC `DependencyLink` stays unchanged).
  - Ids lower-cased on ingest and query; tag values always strings (booleans `"true"`).
  - Reporter: 512 spans per POST, compression `none` (exporter default `gzip`), ingest retried
    (idempotent), 400/413 permanent `VALIDATION`.
  - Any call on a closed client → `CANCELLED` ("client is closed"); `initTracing` → `CONFIG`.
- **Wire traps**: span times are epoch **µs**, query `endTs`/`lookback` **ms**; error bodies are
  plain text (`text/*`); Zipkin lower-cases service and span names; one bad span (e.g. a boolean
  tag) rejects the whole batch; in-memory storage groups traces by the low 64 id bits (use
  distinct random ids in tests); `autocompleteKeys` needs `AUTOCOMPLETE_KEYS` on the server.
- **Docker**: `docker/compose.yml` runs `openzipkin/zipkin:3.6.1` (in-memory storage,
  `AUTOCOMPLETE_KEYS=grow.test,http.method`, `COLLECTOR_GRPC_ENABLED=true`); `bootstrap/` waits
  for `/health` + the query API, checks the version and writes `/bootstrap/env`
  (`GROW_ZIPKIN_URL`, `ZIPKIN_URL`, `OTEL_EXPORTER_ZIPKIN_ENDPOINT`, `ZIPKIN_VERSION`, …). It
  ingests nothing; every language uses its own service names.
- Unit-test-only cases and server/language differences: `docs/compatibility.md`.

## Rules for agents

- Keep secrets out of code, tests, fixtures, logs and commit messages. Credentials are always wrapped
  in the redacting secret type; error messages pass through redaction.
- Runtime dependencies must use a licence from the allowlist: Apache-2.0, MIT, BSD-2-Clause,
  BSD-3-Clause, ISC, Zlib, Unicode-3.0, Unicode-DFS-2016, 0BSD, CC0-1.0, MPL-2.0. Never GPL, LGPL,
  AGPL, SSPL, BUSL or EPL at runtime.
- Keep dependencies small; prefer the standard library.
- Before you push: `make lint coverage` for every language you touched (or all of them for shared
  changes), and `make test-docker LANGS="<lang>"` when behaviour against the service changed.
- Update the README function overview, `docs/` and the skill file when the public API changes.
